Install Beelot

Install from the apt repository

On Debian 13, Ubuntu 24.04 or later (amd64 or arm64), install Beelot from its signed apt repository on GitHub Pages; apt upgrade then follows the releases.

sudo install -d -m 0755 /etc/apt/keyrings
curl -fsSL https://mederel.github.io/beelot/beelot.asc | sudo tee /etc/apt/keyrings/beelot.asc > /dev/null
sudo tee /etc/apt/sources.list.d/beelot.sources > /dev/null <<'EOF'
Types: deb
URIs: https://mederel.github.io/beelot
Suites: stable
Components: main
Signed-By: /etc/apt/keyrings/beelot.asc
EOF
sudo apt update
sudo apt install beelot

The package installs the server, its frontend and a beelot systemd service running as the beelot user, and recommends mariadb-server. It does not create the database and does not start the service at install, but it enables it: once configured, it starts at every boot (a start that fails five times in a minute, for example before the database is set up, is not retried).

  1. Create the database and its user in MariaDB (choose your own password):

    CREATE DATABASE beelot;
CREATE USER 'beelot'@'localhost' IDENTIFIED BY '<password>';
GRANT ALL ON beelot.* TO 'beelot'@'localhost';

  2. Edit /etc/beelot/beelot.env: uncomment BEELOT_DATABASE_PASSWORD and set it to that password and, if the database is elsewhere, uncomment BEELOT_DATABASE_URL and set it. The file lists every setting of the configuration table, commented out with its default. It holds the password, so only root and the beelot group can read it; an upgrade never overwrites your edits.

  3. Start it: sudo systemctl start beelot. The logs are in journalctl -u beelot. The database tables are created and migrated at startup.

Tables in progress are saved in the database as they change, so that restarting the server (an update, say) does not end a game: at startup it brings back the tables active in the last two hours, with their ids, seats, tokens and codes. Their seats are disconnected until the players' pages reconnect. A saved table is deleted when it ends or two hours after its last activity; the nightly job removes any a crash left. A table the server cannot read back is dropped with a warning.

The server listens on 127.0.0.1:8080: put a proxy in front of it, as in Serve over HTTPS. To remove the package and its settings: sudo apt purge beelot (the beelot user and the database are left alone).

Update automatically (apt)

packaging/debian/beelot-auto-update checks the Beelot repository once an hour and installs a newer version when there is one, then restarts the service. It stops at the first problem: a conflict or a failed install (nothing is restarted), a failed systemctl restart beelot, or a service that is not running a few seconds later. Only the Beelot repository is refreshed, only the beelot package is upgraded, nothing is removed and the configuration files are kept as they are. The service is restarted only if it was running.

The package installs the script as /usr/sbin/beelot-auto-update and its schedule as /etc/cron.d/beelot-auto-update (a configuration file: edit the minute or MAILTO there, or delete the file to turn the updates off; an upgrade keeps your change). It needs a cron daemon, such as cron.

After a failure the script remembers the version it could not install and does not try it again each hour; cron mails the output to MAILTO (root by default). Read the log (journalctl -t beelot-auto-update), fix the cause, then sudo rm /var/lib/beelot-auto-update/failed. The message names the previous version, to go back with sudo apt install beelot=<version>. A database migration that a new version has already applied is not undone by going back.

Install the RPM (Fedora, Rocky Linux, AlmaLinux)

Releases also build beelot-<version>-1.x86_64.rpm (amd64) and beelot-<version>-1.aarch64.rpm (arm64), served from a signed dnf repository on GitHub Pages, so dnf upgrade follows the releases. Add the repository, then install:

sudo curl -fsSL https://mederel.github.io/beelot/rpm/beelot.repo -o /etc/yum.repos.d/beelot.repo
sudo dnf install beelot
sudo dnf install mariadb-server      # or use a database elsewhere

The .repo file turns repo_gpgcheck on and fetches the public key from https://mederel.github.io/beelot/beelot.asc (the apt repository's key): dnf checks the signature of the repository's index, which lists the SHA-256 of every package. The packages themselves are not signed one by one (gpgcheck=0). To install without the repository, download the file from the latest release and run sudo dnf install ./beelot-<version>-1.<arch>.rpm (x86_64 or aarch64).

Then follow steps 1 and 2 above (the database and /etc/beelot/beelot.env, which is root:beelot, mode 0640, and kept when you upgrade). Following RPM convention, the install neither enables nor starts the service: sudo systemctl enable --now beelot. An upgrade restarts it if it is running. The package needs the glibc of its build image (2.39), so dnf refuses it on RHEL 9 and its clones (glibc 2.34); use Fedora 40 or later, RHEL 10 or a clone of it. Removing it (sudo dnf remove beelot) keeps the beelot user and the database, and an edited settings file is saved as beelot.env.rpmsave.

Container image

Each release publishes ghcr.io/mederel/beelot:<version> and :latest for amd64 and arm64 (one multi-architecture image: docker pull takes the machine's own; <version>-amd64 and <version>-arm64 name each one, and the arm64 image appears a few minutes after the amd64 one): the release's own server binary and frontend on Debian 13, running as the unprivileged user 10001, listening on 0.0.0.0:8080 inside the container, with the settings of the configuration table read from the environment. The image has no volume: all state is in the MariaDB database, so the container can be replaced at any time (games in progress end and players are signed out). Like the other packages, it refuses to start until the privacy settings and the IP token secret are set, and its log names what is missing.

The image has a HEALTHCHECK on GET /api/health, next to GET /api/version (the running version): it answers 200 with {"status":"ok"} when the server reaches its database and 503 with {"status":"unavailable"} when it does not. The route needs no sign-in, is not rate limited, never shows an error or any setting, and reads and writes nothing; a proxy or a monitor can use it the same way.

An operator can see the server's state on GET /admin/status (US-152). The page is off unless BEELOT_ADMIN_TOKEN is set (at least 16 characters; the server refuses a shorter one). Then it asks for the token in a form, which sets a cookie for 30 minutes, or accepts Authorization: Bearer <token> from a monitor. It shows the version, how long the server has run, the database state, the open tables by kind, the number of connected players and the last warnings and errors of the log. It holds no names, tokens or addresses and changes nothing.

packaging/container/compose.yaml runs it with MariaDB and a database volume:

cd packaging/container
cp .env.example .env && $EDITOR .env      # fill in every change-me
docker compose up -d

It publishes the port on the host's loopback only (127.0.0.1:8080): put a reverse proxy that terminates TLS in front of it as in Serve over HTTPS, set BEELOT_PUBLIC_URL to the address players type and, if the proxy is the only way in, BEELOT_TRUST_FORWARDED_HEADERS=true. To update, docker compose pull && docker compose up -d; pin BEELOT_VERSION in .env to stay on a release. Take a database backup first, as a release can migrate the schema (see Back up and restore).

The first image pushed creates a private package: in the repository's Packages, open beelot, Package settings, and change its visibility to public once, so that docker pull works without a login. CI builds the image from the same binary and runs it against a MariaDB container, on amd64 and on arm64, on every pull request.

Arch Linux

packaging/arch/ holds a PKGBUILD that builds a tagged release from source (it needs cargo; the build takes a few minutes). It installs the same files as the other packages, with the unit disabled, a sysusers.d file for the beelot user and a tmpfiles.d file that gives /etc/beelot/beelot.env the owner root:beelot and mode 0640. The settings file is a pacman backup file, so an upgrade keeps your edits (a changed default is written as .pacnew).

git clone https://github.com/mederel/beelot && cd beelot
packaging/arch/prepare-pkgbuild.sh <version> /tmp/beelot-pkg   # fills in pkgver and the checksum of the tag
cd /tmp/beelot-pkg && makepkg -si
sudo systemctl enable --now beelot                              # after steps 1 and 2 above

CI builds, installs and checks this package in an Arch container on every pull request. A maintainer who wants it on the AUR copies the output of prepare-pkgbuild.sh for the release, generates .SRCINFO with makepkg --printsrcinfo > .SRCINFO and pushes both to the AUR repository of the package beelot; nothing here publishes it.

Gentoo

packaging/gentoo/ is a small overlay (beelot) with the package games-board/beelot, built from a tagged release with cargo.eclass and your own flags, and the acct-user/beelot and acct-group/beelot packages that create the service user. It installs the same files as the other packages (/usr/bin/beelot-server, /usr/share/beelot/static, and /etc/beelot/beelot.env, root:beelot mode 0640, kept by CONFIG_PROTECT when you update) and supports both init systems: the systemd unit and an OpenRC script (supervise-daemon, run as beelot, reading the same /etc/beelot/beelot.env; quote a value that holds spaces or shell characters). Neither is started or enabled by the install. The mariadb USE flag (on by default) only adds a dependency on MariaDB; switch it off to have the database on another machine.

The ebuild lists every crate of Cargo.lock, and their licences, so it changes with each release. Every release therefore carries the ready-made overlay, beelot-gentoo-overlay-<version>.tar.gz, with that release's ebuild and its Manifest (it appears some minutes after the release). Replace the overlay's directory with it to install or update:

sudo rm -rf /var/db/repos/beelot && sudo mkdir -p /var/db/repos/beelot
curl -fsSL https://github.com/mederel/beelot/releases/download/v<version>/beelot-gentoo-overlay-<version>.tar.gz \
  | sudo tar -xz -C /var/db/repos/beelot
printf '[beelot]\nlocation = /var/db/repos/beelot\n' | sudo tee /etc/portage/repos.conf/beelot.conf
echo 'games-board/beelot ~amd64' | sudo tee /etc/portage/package.accept_keywords/beelot
sudo emerge --ask games-board/beelot
sudo rc-update add beelot default && sudo rc-service beelot start   # or: systemctl enable --now beelot (steps 1 and 2 above first)

To build the overlay yourself, from a checkout of the release's tag (python3, cargo with network access, and ebuild for the Manifest), run sudo .github/scripts/prepare-ebuild.sh <version> /var/db/repos/beelot.

CI runs pkgcheck scan on the overlay and, in a gentoo/stage3 container with dev-lang/rust-bin, compiles the server, installs the image, merges it and removes it again. It is a separate job that runs only when packaging/gentoo/, its scripts or Cargo.lock change, because compiling there takes long. Publishing the package to GURU or ::gentoo is left to a maintainer: commit the generated games-board/beelot/beelot-<version>.ebuild and its Manifest there.

The root of the Pages site is a presentation page, written once in pages/ (index.html, site.css, site.js) and copied by build-apt-repo.sh with the newest release number. Set the repository variable BEELOT_PLAY_URL (no trailing slash) to the address of a hosted game to add the page's links to it.
