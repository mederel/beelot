OpenTelemetry

The server can send its logs (US-154), its metrics (US-155) and its traces (US-156) to an OpenTelemetry collector over OTLP. It is off unless an endpoint is set, and it is configured only by the standard variables of OpenTelemetry, in the environment or in /etc/beelot/beelot.env:

Variable Default Meaning
OTEL_EXPORTER_OTLP_ENDPOINT, or OTEL_EXPORTER_OTLP_LOGS_ENDPOINT, OTEL_EXPORTER_OTLP_METRICS_ENDPOINT and OTEL_EXPORTER_OTLP_TRACES_ENDPOINT for one signal unset the collector's http or https address, such as http://collector:4318; unset, nothing is exported
OTEL_METRIC_EXPORT_INTERVAL 60000 milliseconds between two exports of the metrics
BEELOT_BROWSER_TRACES false true makes the web client send its spans (needs the traces exported)
OTEL_TRACES_SAMPLER, OTEL_TRACES_SAMPLER_ARG parentbased_always_on the standard sampler, such as parentbased_traceidratio with 0.1 to keep one trace in ten
OTEL_EXPORTER_OTLP_HEADERS unset headers sent with each export, such as authorization=Bearer ...
OTEL_EXPORTER_OTLP_PROTOCOL http/protobuf the only protocol Beelot exports with; anything else stops the start
OTEL_SERVICE_NAME beelot the service.name of the records
OTEL_RESOURCE_ATTRIBUTES unset more resource attributes, key=value,key=value
OTEL_SDK_DISABLED false true turns the export off whatever the endpoint

A bad endpoint or protocol stops the start with a message that names the variable. A record holds the time, the severity, the target of the event as the instrumentation scope, the message as the body, and the resource attributes service.name, service.version and service.instance.id (new at each start). It holds nothing else: the other fields of an event (names, tokens, addresses) are never read, and only events of Beelot's own crates are sent. RUST_LOG picks what is sent as it picks what is printed; the standard output and the status page work as before. The records leave on their own thread through a queue of 2048: a collector that does not answer drops records and never slows a match, and the pending records are sent when the server stops (five seconds at most).

The metrics (all names start with beelot. except the standard HTTP one; the temporality is cumulative):

Instrument Type Unit Attributes
http.server.request.duration histogram s http.request.method, http.route (the matched template, or unmatched), http.response.status_code
beelot.tables.open gauge beelot.table.kind (local, private, public)
beelot.players.connected gauge none: human players with an open event stream at their seat
beelot.matches.started counter beelot.table.kind
beelot.matches.completed counter beelot.table.kind
beelot.database.up gauge none: 1 when the database answered the last check (every 15 seconds), else 0

No attribute holds a player, an account, a table identifier, an address or a path as requested, so the number of series is bounded by the routes, the methods, the status codes and the three table kinds. There is no /metrics route: to chart them in Prometheus, send them through a collector with a prometheus exporter, or to Prometheus's own OTLP receiver.

The traces: every request has a server span named {method} {route} (GET /api/tables/{id}; the template, never the path asked for) with http.request.method, http.route and http.response.status_code, and the status error for a 5xx. A traceparent header makes it a child of the caller's trace (W3C Trace Context), but only when the header is trusted: with BEELOT_TRUST_FORWARDED_HEADERS=true (a proxy is the only way in and forwards it), or, with BEELOT_BROWSER_TRACES=true, on the calls the browser says come from its own page (Sec-Fetch-Site: same-origin). From any other caller the header is ignored: the request starts its own trace and the sampler decides, so a client cannot force sampling or choose a trace id. Under it, each database call of the repository functions is a span beelot.db {module}.{function} (beelot.db sessions.insert) with db.system.name=mariadb and no statement, and each table action is a span beelot.table act with beelot.table.kind. Nothing else is traced, and no span holds more attributes than these: no query string, address, name, token or identifier. The log records written while a request is answered carry its trace_id and span_id, so a log line leads to its trace and back.

Traces from the browser (US-158). With BEELOT_BROWSER_TRACES=true (and the traces exported), the web client makes a span per call to /api/ and per WebSocket, puts a traceparent header on its calls, so the server's span is the child of the browser's, and sends the finished spans to POST /api/telemetry/spans, which forwards them to the collector as the service beelot-web. The browser never learns the collector's address. The route takes at most 64 KiB and a hundred spans per request, counts against the usual per-client limit, and keeps only the method, the route with every segment that has a digit or is long replaced by {id}, the status, whether the call failed, and for an uncaught error the name of its type: never a message, a stack, a query string or anything typed. It also says whether the page was opened by the Android app (its android-app:// referrer) or not: beelot.client.platform is android-app or web, and a page loaded again by a navigation inside the app (after signing out, for example) counts as web, because the answer is not stored. The dashboard of the observability profile has a panel of the requests and errors by platform. No cookie or storage is created. Without the variable the route does not exist and the client does not fetch its tracing script. The privacy policy says so.

A minimal collector that prints what it receives:

receivers:
  otlp:
    protocols:
      http:
        endpoint: 0.0.0.0:4318
exporters:
  debug:
    verbosity: detailed
service:
  pipelines:
    logs:
      receivers: [otlp]
      exporters: [debug]
    metrics:
      receivers: [otlp]
      exporters: [debug]
    traces:
      receivers: [otlp]
      exporters: [debug]
