The OpenObserve stack

packaging/container/compose.yaml has a profile observability that starts OpenObserve next to Beelot: one container that stores and searches the logs, metrics and traces, with a web interface and an OTLP/HTTP receiver, so no separate collector runs. It is AGPL-3.0, like Beelot, and the data stays in the volume beelot-openobserve on your machine.

  1. In .env set OPENOBSERVE_ROOT_EMAIL and OPENOBSERVE_ROOT_PASSWORD, and the two OTEL_* lines of .env.example (the endpoint http://openobserve:5080/api/default and the Authorization header with the Basic token, made by the command written there). OPENOBSERVE_RETENTION_DAYS (14 by default) is how long the data is kept.
  2. docker compose --profile observability up -d, then open http://127.0.0.1:5080 (published on the loopback only; put a TLS reverse proxy in front to reach it from elsewhere).

The service openobserve-setup loads a "Beelot" dashboard (request rate, 95th percentile of the duration and share of 5xx by route, open tables, connected players, completed matches, database up, and the recent warnings and errors) and three alerts. Running it again changes nothing. An alert needs the metric it watches to exist in OpenObserve, and the request metric only appears with the first request, which may come minutes or days after a fresh install: the service stays up, says in its log which alerts it waits for, looks again every 30 seconds (OPENOBSERVE_SETUP_INTERVAL) and loads each alert as its metric appears. It stops by itself after "all the alerts are loaded" (docker compose logs openobserve-setup shows it) and is only restarted when it fails.

Alert Fires when Recovery message
beelot-database-down the database has not answered for 2 minutes beelot-database-down-resolved
beelot-error-share more than 5 % of the requests of the last 5 minutes ended in a 5xx beelot-error-share-resolved
beelot-no-telemetry Beelot sent nothing for 10 minutes: the server or its export is down beelot-no-telemetry-resolved

OpenObserve sends nothing when an alert clears, so each recovery message comes from a companion alert that is true for a while after the recovery (15 minutes, 12 for the telemetry) and sends once. A message holds the alert's name, its state, the time and a link to the dashboard, and nothing else: no log line and no value from a player.

Without a destination the alerts are loaded on a placeholder that goes nowhere. To be told, set in .env (the setup service runs at each up, creates what is missing and moves the alerts from the placeholder):

  • OPENOBSERVE_ALERT_WEBHOOK_URL: any HTTP webhook. OPENOBSERVE_ALERT_WEBHOOK_FORMAT is json (the default; a body {"text": ..., "content": ...} that Slack, Mattermost and Discord accept) or text (the message alone).
  • OPENOBSERVE_ALERT_EMAIL, with OPENOBSERVE_SMTP_ENABLED=true, OPENOBSERVE_SMTP_HOST, OPENOBSERVE_SMTP_PORT, OPENOBSERVE_SMTP_USER, OPENOBSERVE_SMTP_PASSWORD, OPENOBSERVE_SMTP_FROM and OPENOBSERVE_SMTP_ENCRYPTION (starttls, ssltls or off) for the mail server. OpenObserve only mails its own users, so the setup creates the address as an administrator with a random password; reset it as root if that person should sign in.
  • OPENOBSERVE_ALLOW_PRIVATE_DESTINATIONS=true: recent OpenObserve versions refuse a webhook on a private address (a ntfy on your own network); this sets ZO_SKIP_SSRF_CHECKS to allow it. Leave it off for a public webhook.
  • OPENOBSERVE_PUBLIC_URL: the address you reach the web interface by (http://127.0.0.1:5080 by default), for the link.
# ntfy: the topic URL is the secret, and the message is plain text
OPENOBSERVE_ALERT_WEBHOOK_URL=https://ntfy.sh/your-secret-topic
OPENOBSERVE_ALERT_WEBHOOK_FORMAT=text
# Slack: an incoming webhook
OPENOBSERVE_ALERT_WEBHOOK_URL=https://hooks.slack.com/services/T000/B000/XXXX

To use a destination OpenObserve offers that these variables do not, add it by hand in the web interface (Alerts, Destinations), then attach it to the alerts there. Without the profile and without the OTEL_* lines, nothing changes.

The CI starts this stack and the setup service before any traffic, sends traffic, checks that the log line, the request's span and the request metric are searchable, that the dashboard exists and that all six alerts (three, and their recovery messages) are loaded and the setup has ended, stops the database and waits for the alert to reach a webhook (a small listener container), and prints the memory of the container and the size of its image in the log of the step "Test the observability stack". Those figures are not quoted here until they have been read.

To use another backend (OpenObserve Cloud, Grafana Cloud, SigNoz, Honeycomb or any OTLP endpoint), leave the profile off and set OTEL_EXPORTER_OTLP_ENDPOINT and OTEL_EXPORTER_OTLP_HEADERS to what it gives you.
