Develop and verify

Develop

cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --workspace

The server's database tests start a MariaDB container with Testcontainers, so Docker must be running. Building the server needs OpenSSL's development files (libssl-dev on Debian and Ubuntu), which webauthn-rs links against.

To skip the containers, give the tests a MariaDB of their own: start docker run -d --rm -p 3307:3306 -e MARIADB_ALLOW_EMPTY_ROOT_PASSWORD=1 mariadb:12.3 and run BEELOT_TEST_MARIADB_PORT=3307 cargo test --workspace. Every test still gets a fresh database; they are not dropped, so throw the server away afterwards. CI does the same, with one server for the whole run. Not the compose database: its root password is random and its beelot user cannot create databases.

The snapshots the table API sends are pinned by the files in crates/beelot-server/tests/contract/. After an intended change, rewrite them with UPDATE_CONTRACT=1 cargo test -p beelot-server --test api_contract and review the diff.

The table's rules live in crates/beelot-table, which has no web, database or async dependency (a test checks it). The snapshots of every viewer of scripted, seeded matches are pinned, by hash, in crates/beelot-server/tests/golden/; a change of the table must leave them as they are. After an intended change, rewrite them with UPDATE_GOLDEN=1 cargo test -p beelot-server --test table_golden and review the diff.

The frontend

The frontend is Svelte 5 and TypeScript, styled with Tailwind CSS 4 and built with Vite (ADR-007). Its sources are in crates/beelot-server/web/ and the build writes crates/beelot-server/static/, which is committed: the server, the packages and the Rust tests use it as it is, and none of them needs Node. It needs Node 22 or later:

cd crates/beelot-server/web
npm ci             # once, and after a change of package-lock.json
npm run dev        # http://localhost:5173, with the API proxied to the server on :8080 (BEELOT_SERVER to change it)
npm run check      # the type check (svelte-check)
npm run lint       # Biome: format and lint of the TypeScript, JavaScript and JSON (npm run format fixes the format)
npm test           # the tests (Vitest, in a happy-dom page): models, stores, API, table controller, components
npm run build      # writes ../static: commit it with the change of the sources
npm run e2e        # the browser tests (Playwright): Chromium on 14 sizes (phones, landscape, tablets, desktops, a solo round on a few; the layout shift of the table on two; the worst-case names, scores and lists in English, French and Dutch, the font at 200%, and what a phone's browser does: a notch and a home indicator, the keyboard, bars that hide and show, a phone turned on its side; and, on four sizes, accessibility: axe at WCAG 2.2 level AA, the keyboard, reduced motion, forced colours, more contrast, and an orientation that is never locked), WebKit (iPhones, an iPad) and Firefox on the key screens only; needs the server running with `BEELOT_TRUST_FORWARDED_HEADERS=true` (each test is a client of its own; BEELOT_URL, default http://localhost:8080) and `npx playwright install chromium webkit firefox` once

CI runs the type check, the lint, the tests and the build, and fails when the rebuilt static/ differs from the committed one (the build is deterministic). Files copied as they are (the privacy policy, the music, the icons, the manifest) live in web/public/. The content security policy allows no inline script or style: components set styles through style: directives (the CSSOM), never a style attribute or {@html}, and a test checks the sources and the built page. Every text of the page is an English key of t(), translated in src/lib/i18n/fr.ts and nl.ts; a test fails when a text has no French or Dutch.

What each layer of the browser tests catches and costs, how to run one project or one test and read its failure, and how to add a screen or a device: Layout tests.

The tests of the repository's scripts, packages and site are plain Node: node --test crates/beelot-server/frontend-tests/*.cjs.

CI

.github/workflows/ci.yml checks every pull request and every push to main. A first job, changes, reads which files changed (.github/scripts/ci-changes.sh) and the others run only when the change needs them: lint (fmt, clippy, the lock, the repository scripts, the workflows), web (the frontend), rust-test (the tests with coverage) and rust-doc, build (the release server, once for amd64 and once for arm64), then, from that binary, browser, screenshots, lighthouse, package (the Debian packages and RPMs) and stack (the container image, the backup, the observability stack), and arch, gentoo and android; on a pull request that changes the bots or the arena, bots (see Bot arena). A change to the workflows runs everything, and so does every push to main. The required check is the ci job, which waits for the others; on main it is followed by release.yml.

The browser tests run in shards, each on a runner of its own that installs one engine: six for Chromium, three for WebKit, one for Firefox. To run one of them locally, set the engine and the shard: BEELOT_ENGINE=webkit npx playwright test --shard=1/3. The browser-report artifact of a run is one HTML report of all of them (npx playwright show-report on its folder); a failed shard also keeps its traces and the server's log in browser-failure-<engine>-<shard>.

How the page loads on a slow phone

The lighthouse job runs Lighthouse CI against the release server with the mobile profile (a 4× slower CPU, slow 4G) on the home page, the setup sheet and a solo table that the run makes, three runs a page. The budgets are in lighthouse/lighthouserc.json, with the measurements they were taken from: a Performance score of at least 85, a largest contentful paint under 3 s (the goal is 2.5 s), a total blocking time under 300 ms, a cumulative layout shift under 0.1, and a script and a style transfer of the measured size plus 15%. A budget blocks only when it fails twice in a row. The server sends the page's own files gzipped, which is most of what the score rests on. The job's summary lists the median of each page, the report of every run is the lighthouse-report artifact, and a second run adds a large script on purpose, which must fail the budgets. The layout shift of the table is also a browser test (e2e/layout-shift.spec.ts): opening a table, playing a card, opening a sheet and changing the language move nothing under a finger.

To run it, start the server as for the browser tests, then, from the repository's root:

cd lighthouse && npm ci
CHROME_PATH=/usr/bin/google-chrome node run.mjs               # the budgets (BEELOT_URL, default http://localhost:8080)
CHROME_PATH=/usr/bin/google-chrome node run.mjs --sabotage    # the same with a large script added: it must fail
node --test tests/*.test.mjs                                  # the scripts' own tests, no browser needed

Screenshots of the key screens

The screenshots job compares a screenshot of the home, the setup sheet, the auction, mid-trick, the round result, the match end, the lobby and settings, on six sizes (320×568, 375×667, 390×844, a landscape phone, a tablet, a 1280×800 desktop) in English, and the auction in French and the round result in Dutch, with the approved images committed in crates/beelot-server/web/e2e/screenshots/ (60 PNGs, 1×, under 20 MB in all). What moves is frozen: the effects are off, the tables are the recorded snapshots of tests/contract/, the clock is one instant.

Fonts and anti-aliasing differ by machine, so the images are made and compared in Playwright's Docker image of the version pinned in package.json, and nowhere else. With the server running and npm ci done in web/, from the repository's root:

.github/scripts/screenshots.sh                      # compare with the approved images
.github/scripts/screenshots.sh --update-snapshots   # regenerate them
.github/scripts/screenshots.sh -g "the home" --project=screens-desktop   # one screen on one size

On macOS or Windows, whose Docker has no host network, set BEELOT_URL=http://host.docker.internal:8080. CI never updates an image. A failed run keeps the expected, actual and diff images of each failed screen in the screenshots-failure artifact.

When to approve a diff, and when to fix the page. Open the diff images. If the screen changed because the pull request meant it to (a new control, a new colour, a moved panel), regenerate the images with --update-snapshots, look at each new image, and commit them with the change: the new images are the approval, and the reviewer sees them in the pull request. If a screen changed and the pull request did not mean it (a spacing that shifted on one size, a font that fell back, a clipped label), that is a bug in the page: fix the page and leave the images alone. A diff that appears with no change of the page means the Playwright version moved: regenerate the images in the same pull request as the update. The job also runs one page changed on purpose, which must fail, so that the comparison cannot go quiet. To add a screen or a size to the screenshots, see Layout tests.

Solo, pass-and-play and online games are played on one table that fits one screen (US-119 to US-121): the auction is a panel above the hand, and the online lobby is a panel over the empty felt. src/table/game.svelte.ts turns the snapshots into what is shown, in order and at the pace of Settings: the deal, the calls, each card's flight, the trick gathered to its winner, the round's result and the match's end.

CI measures the tests' coverage with cargo-llvm-cov, shows it per crate in the run summary and in a comment on the pull request, and keeps the lcov.info report as the run's coverage artifact. To measure it locally:

cargo install cargo-llvm-cov
cargo llvm-cov --workspace --html --open

Verify

Before a release, check in a browser, with the console open, that these work without errors:

  • a solo Classic game to the end of a round, and a solo Contrée game with a coinche;
  • pass-and-play with two humans;
  • a private table in two browsers: create it, join by code, choose seats, get ready, start, play a trick (both update without reloading) and send a reaction;
  • quick-match in one browser: bots take the empty seats after 60 seconds;
  • closing one browser at a private table: its seat shows a bot 2 minutes later;
  • passkey sign-up, sign-out and sign-in, statistics after a finished match, the data export and the account deletion.
