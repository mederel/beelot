Release build and releases

Release build

cargo build --release

The server is target/release/beelot-server. It finds the frontend in the crate's static/ folder at the path it was built from; when the binary runs elsewhere, copy crates/beelot-server/static/ next to it and point BEELOT_STATIC_DIR at the copy.

Releases

Every push to main that changes more than documentation, and passes the checks, publishes a release: a vMAJOR.MINOR.PATCH tag, a GitHub release and a workflow artifact holding beelot-<version>-linux-x86_64.tar.gz (the server, its static/ folder and the README; run it with BEELOT_STATIC_DIR=static) and the Debian packages and RPMs of both architectures (see Install from the apt repository). The first release is v1.0.0. After that, the version goes up by a minor when a commit since the previous tag is a feature (its subject starts with feat: or feat(scope):), by a major when one is breaking (a ! before the colon, as in feat!: or fix(deps)!:), and by a patch otherwise. Renovate follows it: a major update of a dependency is a breaking commit, a minor update a feat, a patch update a fix. .github/scripts/next-version.sh computes it.

The release compiles nothing: .github/workflows/ci.yml computes the version when the run starts, builds the server with it once per architecture, and tests and packages that binary; once every check has passed it calls .github/workflows/release.yml, which publishes the packages the checks made. Runs on main go one at a time, so two of them never take the same version; when several merges land at once, a waiting run can give way to a newer one, whose release then holds both.

Real devices before a release

Emulation does not show real touch, the device's fonts, the browser's own bars or a slow GPU. Before a release, a person follows the real-device checklist on five devices (about fifteen minutes each), and .github/workflows/real-devices.yml runs the layout checks on three real phones of BrowserStack (an iPhone with Safari and two Android phones with Chrome, listed in real-devices/lib.mjs). It never runs on every pull request: add the label release-candidate to a pull request, or start it by hand (Actions, real-devices, Run workflow) with a pull request number or a release tag. The record of the run (devices, date, version, commit, result) goes to that pull request or to the release's notes, and the people add what they found under it.

This needs a one-time setup: ask BrowserStack for its free plan for open-source projects, then add the repository secrets BROWSERSTACK_USERNAME and BROWSERSTACK_ACCESS_KEY (Settings, Secrets and variables, Actions; the values are on BrowserStack's Automate dashboard, under Access key). Without them the workflow does nothing and succeeds, so a fork or a clone of the repository is not held up.

Publishing the apt repository

Each release also builds beelot_<version>_amd64.deb and beelot_<version>_arm64.deb (built on an arm64 runner before the release), attaches them to the GitHub release and rebuilds the signed apt repository from every release's package, deployed to GitHub Pages. The same job builds the dnf repository (rpm/) from the releases' RPMs and signs its index with the same key, so the setup below covers both. This needs a one-time setup:

  1. Generate a signing key without an expiry that you keep, with a passphrase, in a real terminal (gpg asks for the passphrase through a prompt that needs one):

    export GPG_TTY=$(tty)
gpg --quick-generate-key 'Beelot apt repository <you@example.org>' rsa3072 sign never

    If it fails with agent_genkey failed: End of file (no terminal, for example in an editor's console), have gpg read the passphrase from standard input instead:

    read -rs -p 'Passphrase: ' P; echo
printf %s "$P" | gpg --batch --pinentry-mode loopback --passphrase-fd 0 \
  --quick-generate-key 'Beelot apt repository <you@example.org>' rsa3072 sign never
unset P

    The key's user id is published in beelot.asc, so use an address you are happy to make public. 2. Add it as repository secrets (Settings, Secrets and variables, Actions): APT_GPG_PRIVATE_KEY, the output of gpg --armor --export-secret-keys <key id>, and APT_GPG_PASSPHRASE. 3. Set Pages' source to "GitHub Actions" (Settings, Pages).

Without the secrets the apt-repo job is skipped with a warning naming the missing secret; the release still holds the tarball and the .deb. To rotate the key, make a new one, replace the two secrets and publish a release: users then fetch the new beelot.asc again. The package job of ci.yml builds and checks the packages, and its lint job the repository scripts, on every pull request without any secret.
