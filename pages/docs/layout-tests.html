Layout tests

Every screen of Beelot must fit every phone, tablet and desktop: nothing that scrolls sideways, nothing clipped or hidden under something else, buttons big enough for a finger. Nine layers of checks guard that (US-201 to US-209). This page says what each one catches and what it costs, how to run one of them and read its failure, and what to change to add a screen or a device. The checks live in crates/beelot-server/web/; the paths below starting with e2e/ or tests/ are in that folder. For the rest of the frontend and of CI, see Develop and verify.

The layers

The browser tests (playwright.config.ts) run in the browser job of ci.yml, in ten shards of three workers each: six for Chromium, three for WebKit and one for Firefox. Each shard takes 2½ to 5 minutes. The cost below is the time of the layer's tests added up over every project and shard, measured on the run of main that merged US-209. The shards run in parallel, so wall-clock time is much shorter: about 67 minutes of browser tests finish in under 5. The screenshots and Lighthouse are jobs of their own, and their cost is that job's wall-clock time.

A layer that runs on every size costs its time again for each new size. That is why the long and heavy specs (the solo round, accessibility, layout shift) run only on the sizes whose entry in e2e/devices.ts says so.

Run one project or one test locally

The browser tests are clients of a running server. Start it as the repository's guidelines say, with the forwarded headers trusted: each test is a client of its own, so they do not share one rate limit. Then, in crates/beelot-server/web/:

docker compose up -d --wait && BEELOT_TRUST_FORWARDED_HEADERS=true cargo run -p beelot-server   # from the repository's root

cd crates/beelot-server/web
npm ci && npx playwright install chromium webkit firefox   # once

npx playwright test --project=phone-375                                   # one project: every spec on one size
npx playwright test e2e/key-screens.spec.ts --project=phone-375           # one file on one size
npx playwright test e2e/key-screens.spec.ts --project=phone-375 -g "mid-trick"   # one test
BEELOT_ENGINE=webkit npx playwright test                                  # the projects of one engine only
npx playwright test --list                                                # every project and test, without running them
npx playwright test e2e/key-screens.spec.ts --project=desktop --headed --debug   # watch it, step by step

The server listens on http://localhost:8080; set BEELOT_URL when it is elsewhere, for example BEELOT_URL=http://localhost:9090 npx playwright test --project=desktop. The project names are the name of each entry of e2e/devices.ts. Two specs need no server, the helper's self-test and the matrix: npx playwright test e2e/layout.spec.ts e2e/matrix.spec.ts.

Most layers run the same way: e2e/extremes.spec.ts, e2e/phone-browser.spec.ts and e2e/accessibility.spec.ts are files of the same config. Two have a command of their own: the screenshots and Lighthouse.

Read a failure

A layout check names the element (its role and its name), the invariant and the numbers, for example a button 38 px tall on a touch screen. Often that is enough. When it is not, look at the page as the test saw it:

  • The trace. A failed test keeps its trace (trace: "retain-on-failure") in test-results/, in a folder named after the test and the project. Open it with npx playwright show-trace test-results/<folder>/trace.zip: every step, a snapshot of the page before and after it, the console and the network.
  • The report. Locally the tests print a list. For the HTML report, add --reporter=html, then npx playwright show-report. It links each failure to its trace and, for a screenshot, shows the expected, actual and diff images side by side, with a slider.
  • A screenshot's diff. A failed comparison writes three images beside the trace in test-results/: …-expected.png (the approved image), …-actual.png (the page now) and …-diff.png (the pixels that differ, in red).
  • In CI. The run's browser-report artifact is one HTML report of every shard: download it, unzip it, then npx playwright show-report on its folder. A failed shard also keeps its traces and the server's log in browser-failure-<engine>-<shard>, the screenshots job keeps the three images of each failed screen in screenshots-failure, and Lighthouse keeps every report in lighthouse-report.

A test that fails in CI but not locally is often an engine you did not run. Run it with BEELOT_ENGINE set to that engine and the same project.

Add a screen to the key list

The key screens are the ones a player spends their time on. Each is shown in one step from a recorded snapshot of crates/beelot-server/tests/contract/, served from the page's side by e2e/mock.ts, so it is the same on every run and every size. To add one:

  1. Name it in SCREENS of e2e/screenshot-list.ts. The name is its image's file name.
  2. Show it in SHOW of e2e/screens.ts: open it (serveApi and page.goto, or openTable with a fixture(…) for a table) and wait until it is the screen shown. SHOW is a record over SCREENS, so npm run check fails until the step is there. The screenshots (US-205) and the accessibility checks (US-207) then take the screen without further change.
  3. Check its layout in e2e/key-screens.spec.ts: a test that opens it and calls expectLayout(page, "the screen", TABLE) (TABLE for a table screen, which must not scroll; nothing for a page). This test runs on every size, in WebKit and Firefox, and on the real devices. When an element must break an invariant, add an exemption with its reason and, for the smallest phones only, below.
  4. Its worst case, when it shows names, scores or lists: a case in e2e/extremes.spec.ts with the long values of e2e/extremes.ts, in the four languages.
  5. Pin it. tests/screenshots.test.ts lists the screens and counts the images. Update it, then make the images: one new image for each of the six sizes. Look at each one before you commit it.

A new page that is not a key screen goes in PATHS of e2e/pages.spec.ts, which checks it on every size for the invariants, script errors and policy violations.

Add a device to the matrix

Every size is one entry of DEVICES in e2e/devices.ts, and playwright.config.ts makes a project of each. Adding a device is adding a line:

{ name: "android-384", width: 384, height: 854, profile: { userAgent: ANDROID, deviceScaleFactor: 2.8125 }, reason: "…what it stands for…" },
  • name is the project's name: the size and a word for what it is. reason says what the device stands for, so that nobody removes it, or adds a twin, without knowing.
  • For a phone or tablet Playwright knows, give its descriptor (a name from Playwright's device list: user agent, touch and pixel ratio). For an Android phone, give a profile. A desktop has neither. The width and height are the page's size without the browser's bars.
  • e2e/matrix.spec.ts pins the list: every size the story asked for, unique names, a reason on each, and the projects equal to the entries. It also pins the entries that carry longRound, accessibility or layoutShift, and the engine entries (engine and only). Setting one of those on the new device means updating its expected list there. Run npx playwright test e2e/matrix.spec.ts: it needs no server.
  • To give the device screenshots, add its name to SCREENSHOT_SIZES, update the count in tests/screenshots.test.ts, and make its images. They go in a folder e2e/screenshots/screens-<name>/, and all the images together must stay under 20 MB.

CI needs no change: the shards share the projects out by themselves. A plain Chromium size costs about 2 minutes of test time, which the six Chromium shards share, so a few seconds on each. A WebKit or Firefox entry costs 2 to 6 minutes on fewer shards, and the WebKit shards are already the slowest of the job.

Regenerate the screenshots

Fonts and anti-aliasing differ by machine, so the images are made and compared only in Playwright's Docker image, of the version pinned in package.json. .github/scripts/screenshots.sh runs it against the server on this host. With the server running and npm ci done in web/, from the repository's root:

.github/scripts/screenshots.sh                                            # compare with the approved images
.github/scripts/screenshots.sh --update-snapshots                         # regenerate every image
.github/scripts/screenshots.sh --update-snapshots -g "the home" --project=screens-desktop   # one screen on one size

The images land in e2e/screenshots/, one folder for each size. On macOS or Windows, whose Docker has no host network, set BEELOT_URL=http://host.docker.internal:8080. CI never updates an image. A new image is an approval, so look at each one before committing it. Develop and verify says when a diff is to be approved and when the page is to be fixed.

A layout bug's regression test

A bug fix carries a test that fails before the fix (see AGENTS.md). For a layout bug, that test is one of these:

  • the viewport it was seen on, added to the matrix when no entry has that size, so that every check runs on it from then on; or
  • the screen it was seen on, added to the layout checks (a test of e2e/key-screens.spec.ts, or a case of e2e/extremes.spec.ts when it took a long text or a large number), when the matrix has the size but no test reaches that state.

Run it before the fix, on the project of that size, and watch it fail with the invariant the bug breaks. The pull request also has a before and after screenshot at 375×667.
